# [다른 AI에게 붙여넣기용] MCP 서버 퍼징 연구 — 지금까지 한 것 전체 정리와 질문

아래는 학부 3학년 두 명(KCSE 투고 목표)이 하는 연구의 현재 상태입니다. 교수님 피드백 전체와 우리가 한 일, 실제 숫자, 약한 점을 솔직하게 적었습니다. **연구 기여를 더 높이려면 무엇을 어떻게 해야 하는지** 현실적인 조언을 부탁드립니다. (예산 없음: 유료 API 못 씀. 무료 LLM·로컬 실행·WSL2 Ubuntu만 가능. 터미널 초보.)

## 0. 연구 한 줄 소개
MCP(Model Context Protocol) 서버를 퍼징하는 연구. 제안 모델은 **서버가 허용한 폴더를 읽어서, 경로 인자 필드에 4종류의 경로 입력(경로 이탈 / 경계값 / 유효 / 준유효, 각 25%)을 생성**해 기존 퍼저의 "입력 생성 단계(②)"만 교체한다. 비교 대상은 Random(대조군)과 mcp-fuzzer 0.7.0(기존 오픈소스 MCP 퍼저).

## 2. 서버와 지표
- 서버(모두 Node.js 파일시스템/도구 서버): mcp-server-filesystem 0.6.2(허용 폴더 검사가 `startsWith` 접두어 방식 → `sandbox_secret` 같은 형제 폴더 접두어 우회 결함; CVE-2025-53110과 **같은 종류**라는 주장만 함), @agent-infra 1.2.29(결함 있음), @adpharm-ro 0.1.2(읽기 전용, 결함 없음 = 대조군).
- 지표: 입력 검증 통과율, 정상 실행률, **경로 이탈 성공**(허용 폴더 밖 경로가 오류 없이 처리된 호출 수), 고유 (도구,폴더) 쌍, V8 커버리지(서버 코드 실행 구간 수), 크래시(전부 0). 95% 신뢰구간, Mann-Whitney U 단측.

## 3. 4번(AFL식 공통 틀)에서 한 일
- 진짜 AFL/AFL++는 파일·stdin 네이티브 프로그램용이라 Node/V8 서버에 계측을 못 붙임(AFLNet도 stdio MCP와 안 맞음). Jazzer.js는 서버를 같은 프로세스에서 돌리게 고친 사본으로만 붙음(예비 시험 1회: 444,893회, 경로 이탈 성공 0, 폴더 정보 없음).
- 그래서 **AFL 방식(큐 → 변이 → 호출 → V8 신규 커버리지면 큐 추가)을 직접 구현**(`afl_fuzz.py`)하고, 변이 전략만 바꿈: Random(havoc) / mcp-fuzzer(0.7.0 입력 생성 로직 이식 65% + havoc) / 제안 / LLM. 초기 시드·큐·피드백·호출 수(도구당 1,000회) 동일, 서버별 시드 10개.
- 내 노트북(WSL2)에서 직접 재현. 진짜 mcp-fuzzer 0.7.0 도구를 그대로 돌린 비교(시드 5개)도 함.

## 4. 실제 결과 (평균±95% 구간)
| 서버 | 지표 | Random | mcp-fuzzer(이식) | 제안 |
|---|---|---|---|---|
| old | 경로 이탈 성공 | 0.0 | 0.0 | 25.2±2.9 |
| old | 커버리지 | 228.0 | 232.0 | 303.7±1.0 |
| agent-infra | 경로 이탈 성공 | 0.0 | 0.0 | 36.9±4.8 |
| agent-infra | 커버리지 | 785.0 | 790.0 | 856.4±0.5 |
| adpharm-ro(결함 없음) | 경로 이탈 성공 | 0 | 0 | 0 |

- 시작 입력을 실제 경로로 유리하게 줘도 결론 동일(기존 방식 0.1~1.3, 제안 24.7~35.0, p<0.001).
- 진짜 mcp-fuzzer 도구 그대로: 경로 이탈 성공 0, 커버리지 old 272 / agent 809(이식보다 높지만 제안보다 낮음).
- 입력 검증 통과율은 현재 버전 서버에서 제안 81.6%, mcp-fuzzer 16.5%, Random 14.6%(14,000호출). 단 이 지표는 "파일 없음"도 통과로 세는 관대한 지표라 adpharm-ro에서는 오히려 Random이 더 높게 나옴(지표 문제로 설명).
- **요소 제거**: 경로 이탈 입력을 빼면 23.7 → 0.0(시드 6개 모두 0). 경계값·유효·준유효를 빼도 경로 이탈 성공은 줄지 않음(오히려 증가). 즉 효과는 사실상 "경로 이탈 입력" 하나에서 나옴.
- **비율 민감도**: 경로 이탈 비중을 10%→70%로 올리면 경로 이탈 성공은 거의 선형 증가, 입력 검증 통과율은 선형 감소. 최적 비율은 없음(25%는 중립 기본값).
- **다른 서버**: git 서버(파일시스템 아님)에서도 제안이 앞섬(서로 다른 조합 120.4 vs 2). 시드 20개로 늘려도 동일.
- **LLM 입력 생성 조건 추가**(자동 생성 프롬프트, 응답 그대로 붙여넣기, 정보량은 제안과 동일: 서버 폴더 구조 + 바로 옆 폴더 이름):

| 서버 | LLM(폴더 정보 없음) | LLM(폴더 정보) | 제안 |
|---|---|---|---|
| old | 0.0 | 193.5±66.5 | 25.2±2.9 |
| agent | 0.0 | 254.3±5.9 | 36.9±4.8 |

  → **폴더 정보가 있는 LLM이 제안 모델보다 훨씬 많이 찾음**. 사전에 정한 판정 기준대로 "규칙이 LLM보다 낫다"는 주장은 철회했고, 기여를 "폴더 구조 정보를 입력 생성에 쓰면 경로 처리 결함을 찾는다"로 바꿈. 정보 없는 LLM은 0.

## 5. 지금 내가 생각하는 약점 (연구 기여가 약해 보이는 이유)
1. 핵심 효과가 "경로 이탈 입력 + 서버 폴더 이름을 안다" 하나로 환원된다. 4종류 조합·25%의 필요성은 실험으로 안 나옴.
2. 정보량 같은 LLM이 제안 모델을 이김 → 규칙 기반 생성기 자체의 새로움이 약함. 남는 기여가 "정보를 쓴다"는 아이디어뿐일 수 있음.
3. 그레이박스 가정(서버 폴더를 직접 읽음). 블랙박스에서는 0건.
4. 결함 종류가 하나(경로 검사 접두어 우회), 서버 3~5개, 크래시 0건 → "더 많은 취약점을 찾는다"고 못 씀.
5. 진짜 AFL++ 비교 불가(재구현), 크래시 지표 부실(프로세스 종료 감지 없음), Jazzer.js는 예비.
6. 시드 수 불일치(5 / 10 / 20, 이전 논문 표는 12회), LLM은 1종·프롬프트 1개·풀 1개 공유.
7. 관련 연구(ToFu, VIPER-MCP 등)와 정량 비교 안 함. CVE-2025-53110 같은 종류라는 것만 주장.

## 6. 하고 싶은데 못 정한 것(질문)
1. 위 상황에서 **논문의 기여(claim)를 어떻게 다시 쓰는 게 가장 방어 가능한가?** (예: "서버 구조 정보 기반 입력 생성이 경로 검사 결함 탐지의 핵심 요인임을 통제 실험으로 보임" 같은 실증 연구 기여로 충분한가, 아니면 새 기법이 필요한가)
2. LLM이 더 잘하는 걸 인정한다면 **LLM + 폴더 정보 + AFL식 피드백**을 제안 모델로 삼는 게 나은가? 아니면 규칙 기반의 "재현성·비용 0·설명 가능성"을 장점으로 내세우는 게 나은가?
3. 기여를 가장 크게 올릴 **우선순위 3가지**(예: 결함 종류 확장 SQL/SSRF/명령 주입, 서버 수 확대(공개 MCP 서버 수십 개 대규모 측정), 새 취약점 발견 및 CVE/제보, 진짜 AFL++/Jazzer.js 비교 강화, 블랙박스에서 폴더 목록 도구를 먼저 호출해 정보를 스스로 알아내는 적응형 모델 등)을 현실적인 난이도·소요시간과 함께 알려 달라.
4. **새 취약점을 실제 서버에서 찾아 보고**하는 것이 기여를 가장 크게 올린다면, 학부생이 안전하게(책임 있는 공개) 하는 절차는?
5. KCSE 수준에서 심사위원이 가장 먼저 공격할 지점 3개와 대응 방법.
6. 실험 설계에서 내가 놓치고 있는 **타당성 위협(threats to validity)**이 있는가? (예: 이웃 폴더 4개 고정, 풀 1개 공유, 이식 구현 편향, 지표 정의)
7. 앞으로 2~4주 안에 할 수 있는 현실적인 일정안.
