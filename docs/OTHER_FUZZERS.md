# 다른 오픈소스 퍼저 적용 가능성 점검 (2026-11-23, 1차)

판정 기준(시험 전에 정함): ① 설치됨 ② 대상 서버에 붙음(서버 코드에 계측 가능) ③ 우리 입력(JSON-RPC tools/call)을 만들 수 있음 ④ 폴더 밖 성공 지표를 같은 방식으로 셀 수 있음. 실패는 "붙지 않음 / 붙었지만 폴더 밖 0 / 느림"으로 구분해 기록. 모델 수정은 새 서버로 재검증할 때만.

| 퍼저 | 결과 | 근거 |
|---|---|---|
| Jazzer.js 4.0.0 | ① 설치 성공. ② 서버를 그대로는 못 붙임, **서버 진입 파일을 고친 사본으로 붙임(아래 시험 결과)** | 계측은 같은 프로세스에서 로드한 JS 모듈에만 적용된다. old 서버(`mcp-server-filesystem` 0.6.2)는 `index.js`가 import 즉시 stdio 서버를 시작하고, `validatePath` 등이 export되지 않는다. 서버를 자식 프로세스로 띄우는 방식으로는 계측이 안 된다. |
| AFL / AFL++ | ② **붙지 않음** | 파일·표준입력으로 입력을 받는 네이티브 프로그램용(소스 컴파일 계측 또는 QEMU). Node 서버(V8 JIT)에는 계측 경로가 없고, pip로 설치되는 패키지도 없다(apt 가용 여부는 이 환경에서 확인 못 함). 커스텀 변이기(Python)는 가능하지만 피드백(커버리지)을 줄 방법이 없다. |
| AFLNet | 시험 안 함 | 네트워크 프로토콜 서버용. MCP stdio 전송과 맞지 않음. |

## 결론 (잠정)
- 세 퍼저 모두 **서버를 고치지 않고는** 같은 틀에 붙일 수 없다. 이것이 "AFL식 재구현" 틀을 쓴 정당한 이유이며 논문 한계 절에 근거와 함께 쓸 수 있다.
- 다음 시험 후보: Jazzer.js + 서버 어댑터 (SDK의 InMemoryTransport로 서버를 같은 프로세스에서 구동하도록 서버 진입 파일을 얇게 수정). 성공 시 Jazzer.js의 커버리지 유도 변이와 우리 전략을 비교 가능. 서버 수정이 들어가므로 "원본 서버 그대로"가 아니라는 점을 명시해야 한다.
- 이번에 실행한 것은 설치 확인과 코드 구조 확인뿐이며, 퍼징 실행 결과는 없다.

## Jazzer.js 시험 결과 (old 서버, 서버 수정본, 1회 60초, 시드 1개 — 예비 시험)
- 구성: 서버를 InMemoryTransport로 같은 프로세스에서 구동(`kit/jazzer/`), 입력은 libFuzzer 바이트열 → 도구 8종 중 하나 + 문자열 인자(최대 60자). 폴더 정보는 사용하지 않음(black-box와 동일 조건).
- 결과: 444,893회 실행(약 7,300회/초), 커버리지 210 edges에서 포화(corpus 11), **폴더 밖 성공 0**.
- 내장 Path Traversal 탐지기는 6초 만에 "크래시"를 냈으나 서버의 폴더 검사 이전의 `path.resolve` 호출에서 울린 것이라 우리 기준의 취약점이 아니다 (탐지기 끄고 재실행).
- 해석 주의: 커버리지 단위(번들 전체의 edges)와 호출 수가 우리 틀(V8 구간, 도구당 1000회)과 달라 숫자를 직접 비교하면 안 된다. 폴더 정보 없이 0인 것은 우리 black-box 결과(0건)와 같은 방향이다. 시드 1개·1서버라 결론이 아닌 예비 관찰.
