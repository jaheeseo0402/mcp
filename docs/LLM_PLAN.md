# LLM 입력 생성 비교 계획 (결과를 보기 전에 작성, 2026-11-23)

## 질문
같은 폴더 정보를 가진 LLM이 만든 입력과 우리 4종류 규칙 입력은 폴더 밖 성공에서 차이가 나는가?

## 조건 (AFL식 틀 안, 나머지 모두 동일)
- `llm_blind`: LLM이 폴더 정보 없이 만든 풀에서 경로형 필드를 뽑음
- `llm_tree`: LLM이 폴더 구조·이웃 폴더 이름을 알고 만든 풀에서 뽑음
- 비교 대상: 제안(ours), Random, mcp-fuzzer 포트 (기존 결과 재사용, 같은 시드 1~10, 서버 old·agent·adro)
- 풀은 1회 생성 후 고정(`kit/llm/`). 실험 중 LLM 호출 없음.

## 판정 기준 (미리 정함)
- 주 지표: 폴더 밖 성공 평균 (old, agent), 보조: 정상 처리율, 커버리지.
- `llm_tree` ≥ `ours`(95% 구간이 겹치거나 높음)이면 → "4종류 규칙의 우위"를 주장하지 않고 "폴더 정보 자체가 핵심, 생성 방식(LLM/규칙)은 부차적"으로 결론을 바꾼다.
- `llm_tree` < `ours`(구간이 안 겹침)이면 → 규칙 기반이 LLM 풀보다 낫다고 쓰되, 풀 1회 생성·생성 모델 편향 한계를 적는다.
- `llm_blind`가 0이면 블랙박스에서 LLM도 못 찾는다는 근거로 쓴다.
- 결과가 어느 쪽이든 모델 규칙을 이 결과에 맞춰 고치지 않는다 (고치면 새 서버로 재검증).

## 사전 기준 적용
`llmtree` ≥ `ours` → **"4종류 규칙이 LLM 풀보다 낫다"는 주장은 하지 않는다.** 폴더 정보를 입력 생성에 쓰는 것이 핵심이고, 생성 방식(규칙/LLM)은 부차적이다. `llmblind` 0은 블랙박스 0건 결과와 같은 방향.

## 이 결과를 그대로 읽으면 안 되는 이유 (분석 후 확인)
1. **정보량이 같지 않았다.** `pool_tree`는 이웃 폴더 안의 파일 이름(`sandbox_secret/secret.txt`)까지 알고 만들었다. 제안 모델은 이웃의 폴더 이름까지만 읽는다. 그 결과 LLM 풀은 `read_file`/`search_files`/`write_file`/`get_file_info`/`edit_file`까지 폴더 밖에서 성공시켰고(시드 5개 예비 분석), 제안은 `create_directory`/`list_directory`/`move_file` 3개 도구만 성공시켰다.
2. **풀 작성자가 실험 구조를 알고 있었다.** 풀을 만든 모델(Claude)이 이 연구의 설계(접두사 형제 폴더 `sandbox_secret`)를 알고 있었고, 풀의 상당수가 그 결함을 직접 겨냥한다.
3. **성공 횟수는 풀의 밀도를 반영한다.** 성공 횟수는 취약점을 찾았다는 것과 다르다. 의미 있는 비교는 (a) 어떤 도구에서 찾았는가, (b) 첫 성공까지 걸린 호출 수이다. 제안은 도구별 첫 성공이 51/33/611번째, LLM 풀은 12~108번째(예비, 시드 5개, 내 환경).
4. 커버리지는 제안과 llmtree가 같다(old 303.7 vs 301.6, agent 856.4 vs 857.4). 탐색한 코드 경로는 비슷하다.

## 사후 수정안 (결과를 본 뒤에 추가한 것임을 명시)
- 정보량을 맞춘 `llmtreeq` 조건 추가: `pool_tree`에서 이웃 폴더 안 파일 이름이 들어간 항목만 기계적으로 제거 (`kit/llm/pool_treeq.json`). 실행: `VARS=treeq bash run_llm.sh ...`
- 이 풀도 결과를 본 뒤에 만들어서 편향이 있다. 정직한 대안은 이웃 폴더를 1단계 더 읽도록 제안 모델을 고치는 것이지만, 고치면 새 서버로 재검증해야 한다 (사전 기준).
- 모델 개선 후보(미실행): 이웃 폴더 안 파일 이름까지 후보에 넣기.
