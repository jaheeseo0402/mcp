# lodepng(PNG 디코더·인코더) 구조정보 단계별 퍼징 결과

작성 2026-11-27. 타깃 lodepng(master 7b2893e), 하네스 `lodepng/harness.cpp`(CRC 무시 디코드 후 다시 인코드), AFL++ 4.33c + ASAN 빌드, 한 번 10분(`-m none -V 600`), WSL2 Ubuntu 동시 8개 실행.
반복: L0, L1은 3번, L2, L3는 8번. 단계 정의: L0 `A` 1바이트 / L1 PNG 시그니처 8바이트 / L2 시그니처 + IHDR 청크 머리와 13바이트 필드 + `-x dict.txt`(청크 이름 등) / L3 L2 + 유효한 PNG 3개.
파일: `lodepng_summary.csv`(실험 1), `lodepng_time.png`, `lodepng_final.png`, `lodepng_cov_summary.csv`, `lodepng_cov_functions.csv`, `lodepng_cov.png`(코드 커버리지 분석).

## 1. 실험 1 결과 (10분 시점)

| 단계 | 반복 | 도달 edge (평균, 범위) | 전체 crash | 고유 crash | 서로 다른 버그 |
|---|---|---|---|---|---|
| L0 | 3 | 42.7 (42~43) | 0 | 0 | 0 |
| L1 | 3 | 45.0 (43~47) | 0 | 0 | 0 |
| L2 | 8 | 67.4 (47~120) | 0 | 0 | 0 |
| L3 | 8 | 1079.2 (995~1133) | 0 | 0 | 0 |

- L2와 L3의 edge 차이: Mann-Whitney U=0, p=0.0009. 8번씩 모두 L2는 120 이하, L3는 995 이상이라 분포가 겹치지 않는다.
- L1과 L2의 차이는 작다(p=0.042, 평균 45 → 67). L2에서 82, 99, 120이 나온 3번을 빼면 L2는 47~50으로 L1과 같다.
- 시간 그래프(`lodepng_time.png`): L3는 시드 상태에서 이미 약 890 edge이고, 70초 부근에서 약 1000으로 오른 뒤 10분 끝까지 서서히 느는 정도다. 큐 크기도 같은 모양이다(약 130 → 250). L0~L2는 거의 평평하다.
- crash는 단계와 상관없이 22번 모두 0건이다. 10분 동안 이 하네스에서는 메모리 오류가 나오지 않았다.

## 2. 단계마다 무엇이 열리는가 (코드 커버리지 분석)

`gcc --coverage` 빌드로 모든 반복의 queue와 crash 입력을 다시 실행해 단계별로 밟은 함수와 줄을 센 값이다(`lodepng_cov_summary.csv`).

| 단계 | 실행한 입력 수 | 함수 | 이전 단계에 없던 함수 | 줄 | 이전 단계에 없던 줄 |
|---|---|---|---|---|---|
| L0 | 17 | 29 | 29 | 213 | 213 |
| L1 | 24 | 31 | 2 | 220 | 7 |
| L2 | 146 | 45 | 14 | 344 | 124 |
| L3 | 2049 | 183 | 138 | 2276 | 1932 |

- L0: 초기화·정리 함수와 디코더 입구(`lodepng_decode`, `decodeGeneric`, `lodepng_inspect`)까지만 간다.
- L1(시그니처): 청크 길이를 읽는 함수 2개(`lodepng_chunk_length`, `lodepng_read32bitInt`)만 더 열린다.
- L2(IHDR 필드): 청크 이름 검사(`lodepng_chunk_type_name_valid` 등), 색상 종류 검사(`checkColorValidity`), 픽셀 수 오버플로 검사(`lodepng_pixel_overflow`, `lodepng_mulofl`) 같은 헤더 검증 코드 14개가 열린다. 입구 검사를 지나가는 정도이고 본체로는 못 들어간다.
- L3(유효 샘플): 압축 해제(`inflatev`, `HuffmanTree_*`, `adler32`), 줄 필터 되돌리기(`unfilter`), 인터레이스(`Adam7_deinterlace`), 보조 청크 읽기(`readChunk_tEXt/iTXt/zTXt/iCCP/...`), 그리고 다시 인코딩하는 쪽(`deflate*`, `addChunk_*`, `filter`) 138개가 열린다. 전체 함수의 약 75%, 줄의 약 85%가 L3에서만 처음 밟힌다.

## 3. 읽는 법과 한계

- 이 타깃에서 정보 문턱은 L3(유효 샘플)에 있다. libexif에서는 L2에서 열렸다. 같은 "구조정보를 준다"여도 형식에 따라 문턱 위치가 다르고, PNG는 압축된 본체(zlib)와 CRC가 맞아야 안쪽 코드에 닿기 때문에 필드 구조만으로는 못 간다고 해석한다. 이 해석은 L2 입력이 본체로 못 들어가는 이유(압축 데이터 생성)를 직접 확인한 것이 아니라 함수 목록에서 추정한 것이다.
- crash가 없어서 "정보가 늘면 버그가 늘어난다"는 비교는 이 타깃에서 할 수 없다. 이 타깃에서 말할 수 있는 건 도달 범위의 차이뿐이다.
- L2의 반복 간 편차(47~120)는 퍼저가 우연히 유효한 조각을 만든 정도의 차이로 보이나 원인을 확인하지 않았다.
- L0, L1은 3번뿐이다. 실행 시간은 10분으로 짧다.
- 커버리지 분석의 입력 수는 반복을 합친 값이라 단계끼리 개수가 다르다(L3가 2049개). 입력이 많은 단계가 줄과 함수를 더 밟기 쉬운 편향이 있고, 위 차이는 이 편향보다 크다고 본다(L3 시드 상태에서 이미 edge 약 890).
